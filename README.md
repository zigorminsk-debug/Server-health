# ServerHealth — диагностика причин медленной работы терминального сервера

Консольная программа **ServerHealth.exe** (один самодостаточный файл, .NET 8, Windows x64):

собирает метрики CPU, RAM, дисковой подсистемы, локальной сети (LAN), процессов,
RDS-сессий и журнала событий Windows → анализирует их по встроенным правилам →
выдаёт **отчёт с вердиктом («узкое место» с доказательствами) и чек-листом
конкретных действий по устранению причин зависаний**.

Результат работы — каталог с файлами:

| Файл | Что это |
|---|---|
| `report.txt` | **Главный документ**: конфигурация, сводка метрик, вердикт, топ-процессы, находки с инструкциями, чек-лист действий |
| `report.json` | те же данные в машиночитаемом виде (для автоматизации/Zabbix/Grafana) |
| `samples.csv` | все системные метрики по каждому замеру (разделитель `;`, UTF-8 BOM — открывается в Excel) |
| `processes.csv` | агрегаты по каждому процессу (CPU, память, рост, ввод-вывод, соединения, зависания) |
| `events.csv` | критические события и ошибки журналов Windows |

Сборка exe выполняется **GitHub Actions** (см. [Сборка](#сборка-exe-через-github-actions)).

## Быстрый старт (3 шага)

1. **Скачать exe.** Откройте репозиторий → **Actions** → последний успешный запуск
   *build* → артефакт **ServerHealth-win-x64** → скачайте `ServerHealth.exe`.
   Либо из **Releases**, если релиз создан. Проверьте контрольную сумму (файл `SHA256SUMS.txt`).
2. **Запустить от администратора** на проблемном сервере:
   ```bat
   ServerHealth.exe
   ```
   По умолчанию: 10 минут наблюдения, замер каждые 5 секунд. Можете работать —
   наблюдение идёт в фоне и не мешает (нагрузка от самой программы минимальна).
   Лучше запускать **в момент, когда сервер тормозит** — так связи «причина → симптом» видны напрямую.
3. **Открыть `report.txt`** из каталога `ServerHealth_ГГГГММДД_ЧЧММСС` рядом с exe.
   Раздел 3 — вердикт, раздел 8 — находки с инструкциями, раздел 9 — чек-лист действий.

> ⚠️ Права администратора обязательны для полной картины: соединения по процессам
> (netstat-таблицы), открытые по сети файлы (SMB), часть событий журналов.
> Программа сама предупредит, если прав не хватает.

Быстрая проверка на 1 минуту: `ServerHealth.exe --quick`

## Параметры запуска

| Параметр | По умолчанию | Описание |
|---|---|---|
| `-d, --duration <мин>` | `10` | длительность наблюдения в минутах (можно дробные: `-d 0.5`) |
| `-i, --interval <сек>` | `5` | интервал между замерами (минимум 1) |
| `-o, --out <путь>` | `ServerHealth_ГГГГММДД_ЧЧММСС` | каталог для отчёта |
| `--events-hours <ч>` | `24` | глубина анализа журналов событий (`0` — не читать журналы) |
| `--quick` | — | быстрый режим: 1 минута / интервал 2 с |
| `--no-json` | — | не создавать `report.json` |
| `-q, --quiet` | — | без живой строки прогресса |
| `-h, --help` | — | справка |
| `--version` | — | версия |

Примеры:

```bat
ServerHealth.exe -d 30 -i 10 -o D:\diag\peak        :: 30 минут в час пик
ServerHealth.exe --quick                            :: быстрая проверка
ServerHealth.exe -d 15 --events-hours 72            :: журналы за 3 суток
```

**Коды возврата:** `0` — критических проблем не найдено; `2` — есть CRITICAL-находки
(удобно для скриптов/мониторинга); `1` — ошибка запуска.

**Ctrl+C** — завершить досрочно; отчёт будет сформирован по уже собранным данным.

## Что собирается и анализируется

| Подсистема | Метрики | Источник |
|---|---|---|
| **CPU** | суммарная загрузка, режим ядра/пользователя, DPC/прерывания (драйверы), длина очереди процессора, переключения контекста, загрузка по ядрам; **по каждому процессу**: CPU%, суммарное процессорное время, «лидер» замеров | PDH + Win32 |
| **RAM** | доступная память, commit и % от лимита, занятость файла подкачки, жёсткие страничные ошибки (свопирование), пулы ядра (выгружаемый/невыгружаемый), дескрипторы/потоки/процессы системы; **по каждому процессу**: рабочее множество, частная память (в среднем/максимум/текущая), **скорость роста МБ/час — выявление утечек** | PDH + PSAPI |
| **Диски** | задержки чтения/записи (мс) и очереди по каждому физическому диску, IOPS, поток МБ/с, свободное место и минимальный запас по томам; **по каждому процессу**: чтение/запись Мбит/с и операций/с (файловый ввод-вывод) | PDH + IO_COUNTERS |
| **Сеть (LAN)** | приём/передача Мбит/с и **пакетов/с** по каждому интерфейсу, утилизация канала, ошибки пакетов; TCP по состояниям (ESTABLISHED/TIME_WAIT/CLOSE_WAIT/SYN…), **соединения по процессам**, топ удалённых адресов, UDP-сокеты; **открытые по сети файлы (SMB)** и пользователи; счётчики Server (отказы рабочих элементов) | IP Helper API, NetFileEnum, PDH |
| **Процессы/зависания** | процессы с **зависшими окнами** (не обрабатывают сообщения — IsHungAppWindow) | Win32 |
| **RDS-сессии** | список сессий: ID, состояние, пользователь, домен, имя клиента; активные/отключённые | WTS API |
| **События** | критические события и ошибки журналов System+Application за N часов, группировка по поставщику/коду, пометка событий, **возникших прямо во время наблюдения** | EventLog |
| **Конфигурация** | ОС, CPU, ОЗУ, аптайм, файл подкачки, схема электропитания | реестр, powercfg |

Все системные счётчики читаются по **англоязычным** путям (PdhAddEnglishCounter) —
программа одинаково работает на русской и английской Windows.

Анализ — набор правил с порогами (см. [docs/REPORT_GUIDE.md](docs/REPORT_GUIDE.md)):
каждое правило оценивает серьёзность (CRITICAL / WARNING / INFO), приводит
доказательства цифрами и **готовые команды/шаги исправления** — включая адресные
рекомендации для известных «тяжеловесов» терминальных серверов:
антивирус (MsMpEng), печать в RDS (splwow64/spoolsv), WMI, dwm, svchost, lsass,
IIS (w3wp), SQL Server, 1С (1cv8, 1cv8c, rphost), браузеры и др.

## Как читать отчёт

1. **Раздел 3 «Вердикт»** — оценки подсистем 0–100 и наиболее вероятная причина
   с доказательной базой. Оценка `< 40` = критично, `40–69` = проблема, `≥ 70` = норма.
2. **Раздел 8** — находки. У каждой: симптомы (цифрами), вероятная причина,
   **«Что делать»** (пронумерованные шаги с командами) и «Как проверить, что помогло».
3. **Раздел 9** — сводный чек-лист первоочередных действий (можно отдать исполнителю как задание).
4. Подробные пороги, типовые сценарии «симптом → причина → лечение» и ручные команды
   диагностики — в [docs/REPORT_GUIDE.md](docs/REPORT_GUIDE.md).

Рекомендуемый порядок внедрения исправлений: сделайте замер «до» → внесите
изменения → повторите замер в то же время → сравните оценки подсистем.

## Сборка exe через GitHub Actions

Сборка полностью автоматизирована (`.github/workflows/build.yml`), выполняется на
`windows-latest`, результат — **один exe-файл, самодостаточный** (.NET включён в файл,
устанавливать ничего не нужно).

**Способы запуска сборки:**

1. **Автоматически** — при каждом пуше в `main` или `arena/**`, а также на pull request.
2. **Вручную** — вкладка **Actions** → workflow **build** → **Run workflow** → выбрать ветку → Run.
3. **Релиз по тегу** — пуш тега `v*` (например `v1.1.0`) создаёт GitHub Release с exe:

   ```bash
   git tag v1.1.0
   git push origin v1.1.0
   ```

   либо ручной запуск workflow с галкой **«Создать GitHub Release»** (тогда релиз
   получит тег `v1.0.<номер запуска>`).

**Где забрать exe:** *Actions* → запуск → блок **Artifacts** → `ServerHealth-win-x64`
(внутри `ServerHealth.exe` и `SHA256SUMS.txt`). В Release файл прикреплён к релизу.

**Проверка контрольной суммы:**

```powershell
Get-FileHash .\ServerHealth.exe -Algorithm SHA256   # сравнить с SHA256SUMS.txt
```

**Если SmartScreen/антивирус предупреждат:** файл без цифровой подписи — это ожидаемо.
Проверьте сумму SHA256 и разблокируйте: `Unblock-File .\ServerHealth.exe`.

**Срок хранения артефактов:** 90 дней. После истечения — просто запустите workflow заново.

## Восстановление и пересборка (если что-то сломалось)

### Пересобрать exe без GitHub (локально / прямо на сервере)

Нужен только [.NET SDK 8](https://dotnet.microsoft.com/download/dotnet/8.0):

```bat
git clone <адрес репозитория> && cd Server-health
dotnet publish src/ServerHealth/ServerHealth.csproj -c Release -r win-x64 --self-contained true ^
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true ^
  -p:EnableCompressionInSingleFile=true -o out
:: результат: out\ServerHealth.exe
```

### Если Actions падает

| Симптом | Решение |
|---|---|
| `dotnet restore` не находит `System.Diagnostics.EventLog` | временный сбой nuget.org — перезапустить job (Re-run) |
| Ошибка компиляции после ваших правок | открыть лог шага «Публикация» — там точный файл/строка; локальная сборка (см. выше) даёт то же самое |
| Артефакта нет, хотя job зелёный | проверить шаг «Загрузка артефакта»; убедиться, что вошли в GitHub под учёткой с доступом |
| Релиз не создался по тегу | у тега должно быть имя `v*`; проверить, что репозиторий разрешает Actions создавать релизы (Settings → Actions → General → Workflow permissions → Read and write) |

### Структура репозитория

## Плановый мониторинг (чтобы ловить проблему в моменте)

Разовое наблюдение не всегда ловит «плавающие» тормоза. Поставьте запуск по расписанию
в часы пик (пример: ежедневно 11:00, 15 минут) — от администратора:

```bat
schtasks /Create /TN "ServerHealth мониторинг" /RU SYSTEM ^
  /TR "C:\Tools\ServerHealth.exe -d 15 -i 10 -o C:\HealthLogs --no-json" ^
  /SC DAILY /ST 11:00 /RL HIGHEST /F
```

* Храните отчёты в `C:\HealthLogs` — сравнение «плохого» и «хорошего» дня даёт точный диагноз.
* Код возврата `2` (есть CRITICAL) позволяет построить простую сигнализацию:

```bat
ServerHealth.exe -d 10 -q
if errorlevel 2 ( powershell -c "Send-MailMessage -SmtpServer smtp.corp.local -To admin@corp.local -From health@corp.local -Subject 'Сервер перегружен' -Body 'см. последний report.txt'" )
```

## Ограничения и FAQ

* **Нужен ли .NET на сервере?** Нет — exe самодостаточный (self-contained single file).
* **Какие Windows поддерживаются?** Windows Server 2012 R2…2025 и Windows 10/11 (x64).
  Нужны права администратора для полной картины.
* **Нагрузка от самой программы?** Порядка 1–3% одного ядра при интервале 5 с;
  данные копятся в памяти и пишутся только в конце.
* **Антивирус ругается на exe?** Это неподписанный файл; проверьте SHA256 и разблокируйте
  (`Unblock-File`). Для регулярного использования можно подписать или добавить исключение.
* **«Счётчик недоступен на этой системе»** — часть счётчиков (например, Terminal Services)
  есть только там, где установлена роль RDS; программа продолжит работу без них.
* **Счётчики производительности повреждены** (ошибка на старте) — восстановление:
  `lodctr /r`, затем `winmgmt /resyncperf`, перезапуск программы.
* **Программа не заменяет** профилировщики глубокого уровня (xperf/WPA, ProcMon) —
  она отвечает на вопрос «где узкое место и что делать», а при необходимости углубления
  в отчёте есть готовые команды для этих инструментов.
