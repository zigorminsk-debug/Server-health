# ServerHealth — диагностика причин медленной работы терминального сервера

**ServerHealth.exe** (один самодостаточный файл, .NET 8, Windows x64) собирает метрики
CPU, RAM, дисковой подсистемы, локальной сети (LAN), процессов, RDS-сессий и журнала
событий Windows → анализирует их по встроенным правилам → формирует **отчёт
(веб-страница + текст) с вердиктом и чек-листом конкретных действий по устранению
причин зависаний**.

Три режима работы:

| Режим | Как запустить | Что делает |
|---|---|---|
| **GUI** (по умолчанию) | двойной клик по exe или `ServerHealth.exe -g` | окно мониторинга: живые графики, оценки подсистем, находки, кнопки управления |
| **Постоянный мониторинг** | `ServerHealth.exe --watch` (или `--watch 15`) | бесконечный цикл: каждые 10 (или N) минут — автоматический отчёт в новую папку |
| **Разовый замер** | `ServerHealth.exe -d 30` | консольный замер N минут → отчёт → выход (удобно для планировщика) |

Результат каждого цикла — папка `ServerHealth_ГГГГММДД_ЧЧММСС` с файлами:

| Файл | Что это |
|---|---|
| `report.html` | **Веб-отчёт** (главный): графики CPU/RAM/дисков/сети, топ-процессы, находки-аккордеон с инструкциями; самодостаточный — открывается двойным кликом без интернета; в постоянном режиме обновляется автоматически |
| `report.txt` | тот же отчёт в текстовом виде |
| `report.json` | данные в машиночитаемом виде (для автоматизации/Zabbix/Grafana) |
| `samples.csv` | все системные метрики по каждому замеру (`;`, UTF-8 BOM — открывается в Excel) |
| `processes.csv` | агрегаты по каждому процессу (CPU, память, рост, ввод-вывод, соединения, зависания) |
| `events.csv` | критические события и ошибки журналов Windows |

Сборка exe — **GitHub Actions** (см. [Сборка](#сборка-exe-через-github-actions)).

## Быстрый старт (3 шага)

1. **Скачать exe.** Репозиторий → **Actions** → последний запуск *build* → артефакт
   **ServerHealth-win-x64**, либо из **Releases**. Проверьте SHA256 (`SHA256SUMS.txt`).
2. **Запустить от администратора** на проблемном сервере (двойной клик → GUI,
   кнопка **«▶ Запустить мониторинг»**). Консольный вариант: `ServerHealth.exe -d 10`.
   Лучше наблюдать **в момент, когда сервер тормозит**.
3. **Открыть `report.html`** — вердикт в шапке, оценки подсистем, графики,
   находки с инструкциями «Что делать».

> ⚠️ Права администратора нужны для полной картины: соединения по процессам,
> открытые по сети файлы (SMB), часть событий журналов.

## Графический интерфейс

Двойной клик по `ServerHealth.exe` (лишнее консольное окно закрывается автоматически):

* **карточки оценок** CPU / RAM / DISK / NET (0–100, обновляются после каждого цикла);
* **живой график** CPU, свободной памяти и сети — обновляется на каждом замере;
* вкладки: **Находки и инструкции** (выбор находки → пошаговая инструкция),
  **Процессы** (топ по CPU за цикл), **Журнал**;
* кнопки: запуск/остановка мониторинга, «Открыть последний отчёт», «Папка отчётов»;
* параметры: интервал замера, **период отчёта (по умолчанию 10 минут)**, сколько
  отчётов хранить, авто-открытие отчёта, сворачивание в трей (мониторинг продолжается,
  при критических находках — всплывающее уведомление).

## Постоянный мониторинг (автоотчёт каждые 10 минут)

```bat
:: отчёт каждые 10 минут, бесконечно; Ctrl+C — остановка
ServerHealth.exe --watch

:: отчёт каждые 5 минут, хранить последние 48 отчётов (4 часа истории)
ServerHealth.exe --watch 5 --keep 48
```

Каждый цикл создаёт папку с полным набором отчётов; `report.html` в браузере
**обновляется сам** (meta refresh 30 с) — можно держать открытым на большом экране.
Каталог отчётов по умолчанию: консоль — текущий каталог, GUI — `Документы\ServerHealth`.

Автозапуск вместе с сервером (Планировщик, SYSTEM, при включении):

```bat
schtasks /Create /TN "ServerHealth watch" /RU SYSTEM /SC ONSTART /RL HIGHEST ^
  /TR "C:\Tools\ServerHealth.exe --watch 10 --keep 72 -o C:\HealthLogs"
```

## Параметры запуска (консоль)

| Параметр | По умолчанию | Описание |
|---|---|---|
| (без аргументов) / `-g, --gui` | — | графический интерфейс |
| `-w, --watch [мин]` | 10 | постоянный мониторинг, отчёт каждые N минут |
| `-d, --duration <мин>` | 10 | разовый замер (консоль) |
| `-i, --interval <сек>` | 5 | интервал замера (минимум 1) |
| `-o, --out <путь>` | см. выше | каталог отчётов |
| `--keep <N>` | 0 (все) | хранить N последних отчётов |
| `--events-hours <ч>` | 24 | глубина журналов событий (0 — не читать) |
| `--quick` | — | быстрый замер: 1 мин / 2 с |
| `--no-json`, `--no-open`, `-q` | — | не писать JSON / не открывать HTML / без прогресса |
| `-h, --help`, `--version` | — | справка, версия |

Примеры: `ServerHealth.exe -d 30 -i 10 -o D:\diag` · `ServerHealth.exe --quick` ·
`ServerHealth.exe --watch 15 --keep 96`.

**Коды возврата** (разовый замер): `0` — ок; `2` — есть CRITICAL-находки; `1` — ошибка.

## Что собирается и анализируется

| Подсистема | Метрики | Источник |
|---|---|---|
| **CPU** | суммарная загрузка, режим ядра/пользователя, DPC/прерывания, очередь процессора, переключения контекста, загрузка по ядрам; **по каждому процессу**: CPU%, суммарное время, «лидер» замеров | PDH + Win32 |
| **RAM** | доступная память, commit и % лимита, файл подкачки, жёсткие страничные ошибки, пулы ядра; **по процессам**: рабочее множество, частная память, **скорость роста МБ/час — выявление утечек** | PDH + PSAPI |
| **Диски** | задержки чтения/записи (мс), очереди, IOPS, поток; свободное место по томам; **по процессам**: файловый ввод-вывод | PDH + IO_COUNTERS |
| **Сеть (LAN)** | приём/передача Мбит/с и **пакетов/с**, утилизация канала, ошибки; TCP по состояниям **и по процессам**, топ адресов, UDP; **открытые SMB-файлы** | IP Helper, NetFileEnum, PDH |
| **Зависания** | процессы с зависшими окнами (IsHungAppWindow) | Win32 |
| **RDS-сессии** | ID, состояние, пользователь, клиент | WTS API |
| **События** | критические/ошибки System+Application за N часов, пометка «возникло во время наблюдения» | EventLog |

Счётчики читаются по **англоязычным** путям (PdhAddEnglishCounter) — работает на
RU/EN Windows. Анализ — правила с порогами ([docs/REPORT_GUIDE.md](docs/REPORT_GUIDE.md)),
адресные рекомендации для «тяжеловесов»: Defender, печать RDS, WMI, dwm, svchost,
lsass, IIS, SQL, **1С (1cv8/1cv8c/rphost)**, браузеры и др.

## Как читать отчёт

1. **Карточки оценок** — какая подсистема «виновата» (0–39 критично, 40–69 проблема, 70+ норма).
2. **Вердикт** — наиболее вероятная причина с доказательной базой.
3. **Графики** — динамика за период: видно, что происходит в моменты тормозов.
4. **Находки** — у каждой: симптомы цифрами → причина → **«Что делать»** (команды) → «Как проверить».
5. Подробные пороги и типовые сценарии — в [docs/REPORT_GUIDE.md](docs/REPORT_GUIDE.md).

Порядок внедрения: замер «до» → изменения → повторный замер → сравнение оценок.

## Сборка exe через GitHub Actions

Workflow `.github/workflows/build.yml` (windows-latest) собирает **один самодостаточный exe**.

1. **Автоматически** — при пуше в `main`/`arena/**` и на PR.
2. **Вручную** — Actions → build → Run workflow.
3. **Релиз** — пуш тега `v*`: `git tag v1.1.0 && git push origin v1.1.0` → GitHub Release с exe.

**Забрать exe:** Actions → запуск → **Artifacts** → `ServerHealth-win-x64`, или из Releases.

```powershell
Get-FileHash .\ServerHealth.exe -Algorithm SHA256   # сверить с SHA256SUMS.txt
```

SmartScreen-предупреждение для неподписанного файла — ожидаемо: проверьте сумму и
`Unblock-File .\ServerHealth.exe`. Артефакты хранятся 90 дней.

## Восстановление и пересборка

Нужен только [.NET SDK 8](https://dotnet.microsoft.com/download/dotnet/8.0):

```bat
git clone <адрес репозитория> && cd Server-health
dotnet publish src/ServerHealth/ServerHealth.csproj -c Release -r win-x64 --self-contained true ^
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true ^
  -p:EnableCompressionInSingleFile=true -o out
:: результат: out\ServerHealth.exe
```

Если Actions падает — откройте лог шага «Публикация»: там точный файл и строка ошибки;
локальная сборка даёт тот же результат. Сбой `dotnet restore` (nuget.org) лечится Re-run.

## Плановый мониторинг и профилактика

* Запускайте `--watch` или GUI постоянно в часы пик; храните отчёты и сравнивайте дни.
* Ориентиры здоровья: CPU < 70%, RAM свободно > 15%, задержки диска < 20 мс, канал < 60%.
* Фиксированный файл подкачки, схема «Высокая производительность», антивирусные исключения
  для рабочих каталогов, завершение «мёртвых» RDS-сессий (GPO 4–8 ч).

## Ограничения и FAQ

* **Нужен ли .NET на сервере?** Нет — exe самодостаточный.
* **Windows?** Server 2012 R2…2025, Windows 10/11 x64; запуск от администратора.
* **Нагрузка от программы?** ~1–3% одного ядра при интервале 5 с.
* **Антивирус на exe?** Неподписанный файл — проверьте SHA256, `Unblock-File`.
* **GUI не открылся?** Требуется Windows Desktop (Server с Desktop Experience);
  для Server Core используйте `--watch`.
* **Счётчики повреждены** — `lodctr /r`, затем `winmgmt /resyncperf`.
