# Руководство по отчёту ServerHealth: пороги, сценарии, ручная диагностика

Этот документ — расшифровка того, **как ServerHealth анализирует данные и какие
пороги считает проблемой**, а также справочник типовых сценариев
«симптом → вероятная причина → что делать» и команды ручной диагностики.

---

## 1. Оценки подсистем (раздел 3 отчёта)

Каждая подсистема получает оценку 0–100. Она считается из доли замеров, в которых
метрика выходила за порог, и величины превышения.

| Оценка | Трактовка |
|---|---|
| 70–100 | норма для периода наблюдения |
| 40–69 | есть проблема — разобрать находки WARNING |
| 0–39 | критично — начинать с CRITICAL-находок |

Вердикт = подсистема с минимальной оценкой + доказательная база (цифры).

## 2. Пороговые значения (используются анализатором)

### CPU

| Метрика | Норма | Проблема | Критично |
|---|---|---|---|
| Загрузка CPU (средняя) | < 70% | > 80% | > 90% |
| Доля времени CPU > 85% | 0 | > 25% замеров | > 40% |
| Очередь процессора | < 2 на ядро | > 2×ядер в >15% замеров | постоянно высокая |
| % DPC Time | < 10% | > 15% | > 50% (драйвер-виновник) |
| Context Switches/sec | < 25 тыс. на ядро | больше | — |

**Комментарии.** Очередь процессора — количество потоков, ждущих CPU; устойчиво
высокая очередь при неполном CPU = однопоточное узкое место. Высокий DPC =
проблемный драйвер (чаще NIC/диск/антивирусный перехватчик).

### RAM

| Метрика | Норма | Проблема | Критично |
|---|---|---|---|
| Доступно памяти | > 15% ОЗУ | < 10% | < 5% или < 400 МБ |
| Commit (% лимита) | < 85% | > 90% | > 95% |
| Файл подкачки занят | < 60% | > 80% | ~100% |
| Pages/sec (жёсткие ошибки) | < 50/с | > 100/с | > 300/с постоянно |
| Невыгружаемый пул ядра | < 1 ГБ | > 1.5 ГБ | > 3 ГБ (утечка драйвера) |
| Рост частной памяти процесса | ~0 | > 100 МБ/ч у крупного процесса | — (утечка) |

### Диски

| Метрика | Норма | Проблема | Критично |
|---|---|---|---|
| Avg. Disk sec/Read и /Write | HDD < 15 мс, SSD < 5 мс | > 25 мс | > 50 мс |
| Current Disk Queue Length | < 2 на диск | > 2 в >15% замеров | высокая постоянно |
| Свободно на томе | > 15% | < 10% | < 5% |

Ориентиры пропускной способности: HDD 7200 — 100–150 IOPS, ~150–200 МБ/с
(линейно); SATA SSD — десятки тысяч IOPS. Если поток с диска мал, а задержки
большие — диск «узкий» либо в деградации (проверить журнал: disk/ntfs/stor).

### Сеть

| Метрика | Норма | Проблема | Критично |
|---|---|---|---|
| Утилизация канала | < 60% | > 70% | > 90% |
| Ошибки пакетов на интерфейсе | 0 | растут | — |
| TCP TIME_WAIT | < 5000 | > 8000 | отказы новых соединений |
| Server: Blocking Requests Rejected | 0 | > 0 | — (SMB не справляется) |

### Зависания приложений

Процессы с окнами, не отвечающими более 5 секунд (IsHungAppWindow), — прямой
симптом «программа не отвечает». Если в этот момент CPU/память/диск в норме —
процесс ждёт внешнее (сеть/БД/файл/принтер): смотрите его ввод-вывод и соединения
в разделе 4 отчёта.

## 3. Типовые сценарии

### 3.1 «Всё тормозит после обеда, к вечеру норм»
Вероятно: исчерпание RAM в часы пик (смотрите RAM-оценку, commit, Pages/sec) либо
пик нагрузки на диск. Что делать: находка RAM → добавить память/выселить утечку;
файл подкачки — фиксированный; сравнить отчёты «плохого» и «хорошего» часа.

### 3.2 «Приложения периодически "Не отвечает" у всех пользователей»
Если одновременно: смотреть диск (задержки/очереди) и журнал (disk/ntfs/stor) —
чаще всего деградация хранилища или RAID. Если у одного приложения — смотреть
его строку в процессах: зависшие окна + его IO/соединения.

### 3.3 «Сервер тормозит, но CPU и память в норме»
Классика медленного диска или сети: раздел 5 (задержки) и раздел 6 (утилизация,
ошибки, SMB-очереди). Проверить антивирус на файловых операциях.

### 3.4 «Один процесс грузит CPU» (wmiprvse, MsMpEng, svchost…)
Отчёт сам подставит адресные рекомендации (база знаний в Analyzer.cs):
Defender-исключения, tasklist /svc для svchost, агенты WMI и т.д.

### 3.5 «RDP-сессии подвисают при переключении»
Сеть: утилизация/ошибки; dwm (графика в сессиях); GPO на обои/анимацию;
переподключение «мёртвых» сессий: `query user`, `reset session`.

### 3.6 «Постепенно все всё медленнее, помогает только перезагрузка»
Утечка: рост частной памяти процессов (раздел 4.2, колонка «рост МБ/ч») или
невыгружаемого пула ядра (RAM-находка; poolmon). Перезагрузка — лишь симптоматика.

## 4. Команды ручной диагностики (из отчёта и для углубления)

```bat
:: какая служба внутри процесса
tasklist /svc /fi "PID eq 1234"

:: живой монитор всех подсистем
resmon

:: задержки диска в реальном времени
typeperf "\PhysicalDisk(_Total)\Avg. Disk sec/Transfer"

:: многодневный сбор счётчиков (свой Data Collector Set)
logman create counter SlowTrace -f csv -si 15 -max 1000 ^
  -c "\Processor(_Total)\% Processor Time" "\Memory\Available MBytes" ^
     "\PhysicalDisk(_Total)\Avg. Disk sec/Transfer" "\Network Interface(*)\Bytes Total/sec" ^
  -o C:\HealthLogs\slow -v mmddhhmm
logman start SlowTrace   &  logman stop SlowTrace

:: соединения по процессам
netstat -bno

:: RDS-сессии
query user
reset session <ID>

:: антивирус: статус и исключения
powershell -c "Get-MpComputerStatus; Get-MpPreference | fl Exclusion*"

:: питание
powercfg /getactivescheme
powercfg /setactive 8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c   :: High performance

:: проверка диска без перезагрузки
chkdsk C: /scan

:: глубокое профилирование (Windows Performance Toolkit)
wpr -start CPU -start DiskIO -start Net; wpr -stop trace.etl
```

## 5. Что приложить к обращению в поддержку / вендору

1. `report.txt` (полностью) — с вердиктом и находками.
2. `samples.csv` и `processes.csv` — исходные замеры.
3. Точное время проявления проблемы (совпадает ли с событиями раздела 7).
4. Что уже менялось на сервере (журнал изменений).
